# 大数据处理策略：100 亿行宽表

## 核心原则

**100 亿行数据绝不离库。** GDL 是 pushdown-first 架构：过滤（where）、投影（select）、
聚合（group）、关联（join）、排序（sort）、分页（limit）、采样（sample）全部生成 SQL
下推到源库执行，只有最终的小结果集返回客户端。10 亿/100 亿行的规模由源库（MPP/数仓）
承担，GDL 只做 SQL 生成与结果组装。

## 各算子的大数据行为

| 算子 | 行为 | 内存 |
|---|---|---|
| where/select/sort/limit/distinct | 纯 SQL 下推 | O(1) |
| group（聚合） | 纯 SQL 下推 | O(分组数) |
| join/union/subtract/intersect | 纯 SQL 下推 | O(1) |
| sample(n) | `ORDER BY RAND() LIMIT n` 下推 | O(n) |
| sample(n, seed) | 方言支持 seed 则下推；SQLite 走内存确定性采样 | O(n) / O(全表) |
| validate | 违规 `COUNT(*)` 下推，通过则透传 | O(1) |
| describe | **聚合下推**：按列分批 `COUNT/COUNT DISTINCT/MIN/MAX/AVG`，单遍扫描 | O(列数) |
| pivot | **两次查询下推**：DISTINCT 取透视值 + `AGG(CASE WHEN)` 单遍聚合 | O(分组数×透视值数) |
| collect/writeCsv | 全量加载到内存 | **O(结果集)** ⚠️ |
| cache | 全量加载到内存 | **O(结果集)** ⚠️ |

## 已落地的优化

### pivot 下推（本轮新增）

此前 `pivot` 在 JDBC 引擎上会**全量拉取**上游数据到内存再重塑，
100 亿行宽表必 OOM。现改写为两次查询：

1. `SELECT DISTINCT pivotCol ... WHERE pivotCol IS NOT NULL ORDER BY 1`
   取透视值（小结果）；
2. `SELECT groupCols, AGG(CASE WHEN pivotCol='v' THEN valueCol END) AS "v", ...`
   `FROM (上游) GROUP BY groupCols` —— 单遍扫描聚合。

别名规则与内存版一致（原值加双引号、内嵌引号转义、冲突追加序号），
结果列名统一转小写。链中位置时结果物化为临时表（仅分组数×透视值数行），
上层继续纯 SQL。无透视值时返回仅分组列的空结果（旧内存版此处会生成非法 SQL，
已一并修正）。

### describe 下推（本轮新增）

此前 `describe` 在 JDBC 引擎上会**全量拉取**上游数据到内存再统计，
100 亿行宽表必 OOM。现改写为：

1. `WHERE 1=0` 零数据取列元数据（不传输任何行）；
2. 按 50 列分批生成聚合 SQL，一次扫描算出每列的
   `COUNT(*)` / `COUNT(col)` / `COUNT(DISTINCT col)` /
   `MIN(CAST AS VARCHAR)` / `MAX(CAST AS VARCHAR)`，数值列再加 `AVG(CAST AS DOUBLE)`；
3. Java 侧组装为与内存版同格式的 8 列结果（column_name/data_type/row_count/
   null_count/distinct_count/min_value/max_value/avg_value）。

全程 O(1) 内存，100 亿行宽表也安全。链中位置时结果物化为临时表（仅列数行），
上层继续纯 SQL。

### 列名小写统一（前置）

JDBC 引擎读取结果时列名统一转小写，H2 的大写折叠与 SQLite/MySQL 的原样保留
不再导致跨源不一致；下推 SQL 引用列时遵循"简单标识符不加引号"规则，
与各库的标识符折叠行为对齐。

## 使用建议（100 亿行宽表）

1. **先聚合再取数**：`from(t).where(...).group(...).collect()` ——
   100 亿行在库内聚合成几千行后再返回，这是标准用法。
2. **探查用 describe**：已下推，可直接对全表执行。
3. **质量门禁用 validate**：计数下推，通过零拷贝。
4. **避免**：对 100 亿行直接 `pivot` / `collect()` / `writeCsv` 全量——
   这些是内存算子，大结果集会 OOM。如需导出全量，请先 `group` 聚合
   或 `sample` 采样，把结果集降到内存可承受范围。
5. **宽表**：`select` 只取需要的列（列裁剪下推），减少传输；
   describe 按 50 列分批聚合，单条 SQL 不会过长。

## 诚实边界

- `collect()` / `writeCsv` 全量装入内存是语义使然（调用方需保证结果集规模）；
  如需导出大结果集，请先 `group` 聚合或 `sample` 采样降规模。
- `collect()` 返回内存 `RowDataFrame`，语义上就是"全量装入内存"，
  调用方需自行保证结果集规模。
- raw SQL（`where(String)` 等）是逃生口，其大数据行为由所写 SQL 自行负责。
