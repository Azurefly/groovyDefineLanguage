# GDL 性能调优指南

## 基准数据（2026-10-11，10 万行，H2）

| 场景 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| registerTable 物化 10 万行 | 2497ms | 1345ms | 46% |
| 内存引擎 where 查询（平均） | 377ms | 247ms | 34% |
| JDBC 下推 where+group | 777ms | — | 基准 |

## 优化原则

### 1. 优先下推，次选内存

JDBC 数据源的过滤/聚合尽量让数据库执行：

```groovy
// 好：WHERE 下推到数据库，只返回 100 行
from(ds, "orders").where("status = 'OPEN'").collect()

// 差：先全量拉取再过滤（仅当需要内存算子时）
// 内存算子（pivot/describe/window）会自动物化，但尽量把 where 放前面
from(ds, "orders").where("status = 'OPEN'").pivot("month", "sum(amount)")
```

### 2. 连续 where 会自动合并

```groovy
// 这三行会合并为单个 WHERE ... AND ... AND ...，只产生一层子查询
df.where("a > 1").where("b < 2").where("c = 3")
```

### 3. 批量写用 saveBatch

```groovy
// 2000 条：saveBatch 一次往返；循环 save 则是 2000 次往返
tool.saveBatch(records)
```

### 4. 大数据用下推算子

`describe()` 和 `pivot()` 已实现 JDBC 下推（两次查询，O(1) 内存），
100 亿行宽表安全。详见 `11_大数据处理策略.md`。

### 5. 监控慢查询

```bash
# 设置慢查询阈值（默认 1000ms）
-Dgdl.metrics.slowQueryMs=500

# 查看指标快照
GdlMetrics.get().snapshot()
# => {counter.jdbc.write=123, timer.jdbc.write={count=123, avgMs=5, maxMs=120}, ...}

# 关闭指标（极致性能场景）
-Dgdl.metrics.enabled=false
```

### 6. 连接池调优

```bash
# Hikari 连接池
-Dgdl.jdbc.pool.maximumPoolSize=20
-Dgdl.jdbc.pool.connectionTimeoutMs=5000
```

## 已实现的引擎优化

- **ResultSet 转换**：缓存列名数组，批量构造 Row（-27% 查询耗时）
- **registerTable**：事务包裹批量插入，每 5000 行一批（-46% 物化耗时）
- **WHERE 合并**：连续 where 合并为单个 AND 条件，减少子查询嵌套
- **窗口物化**：hop/tumble/cumulate 后链 group() 时自动物化为临时表

## 待优化（已知）

- InMemoryEngine 的 H2 物化对超大数据仍是瓶颈；考虑 Arrow 列存
- Join 下推已支持，但多表 join 顺序未做代价优化
- 流式数据源（Kafka/Fluss）当前为批量快照，非真流
